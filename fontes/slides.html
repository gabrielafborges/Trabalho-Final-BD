Cenário, problema e delimitação

O problema

  • Clientes compram ingressos de shows, teatro, esporte e congressos pela internet.
  • Os ingressos precisam ficar segurados por alguns minutos durante o pagamento.
  • O organizador acompanha faturamento, ocupação e ranking de eventos.

Recorte

  • Catálogo de eventos com setores e preços
  • Clientes e pedidos de ingressos
  • Experiência de compra em tempo real

Objetivos

  • Modelar eventos, clientes e pedidos no MongoDB com embutidos e referências
  • Responder consultas e agregações do organizador
  • Usar o Redis para sessão, reserva com prazo, cache, fila e ranking
  • Demonstrar os dois bancos trabalhando no mesmo fluxo

Fora do escopo: QR Code, reembolso, cupons, assentos numerados, pagamento real.

Um cenário, dois bancos

MongoDB - dados permanentes

  • eventos: título, data, cidade, local e setores embutidos
  • clientes: dados cadastrais, endereço embutido, preferências
  • pedidos: referência a cliente e evento, itens embutidos
  • Consultas com operadores, Aggregation Pipeline e índices

Redis - dados rápidos e temporários

  • string + TTL: sessão, reserva de ingresso, cache da página
  • hash: resumo rápido do evento e do cliente
  • sorted set: eventos mais vendidos e mais acessados
  • list: fila de pagamento, histórico recente
  • set: clientes online, favoritos

Regra do projeto: o MongoDB é a fonte da verdade; o Redis guarda o que expira, o que precisa de resposta imediata e o que pode ser reconstruído a partir do MongoDB.

Modelagem do MongoDB

ColeçãoCampos principaisEstratégia
eventos (8)titulo, categoria, data, cidade, local{nome, capacidade}, setores[{nome, preco, capacidade, vendidos}], tags[], statusdocumentos embutidos
clientes (8)nome, email, telefone, endereco{cidade, uf}, preferencias[], dataCadastro, ativodocumento embutido
pedidos (12)clienteId, eventoId, dataPedido, status, formaPagamento, itens[{setor, quantidade, valorUnitario}], valorTotalreferências + embutidos

Por que embutir?

local, setores, endereco e itens pertencem só ao documento pai e são sempre lidos junto com ele. Evita $lookup em toda leitura. O valorUnitario do item guarda o preço histórico.

Por que referenciar?

Um evento tem milhares de pedidos. Embutir o evento/cliente em cada pedido duplicaria dados e exigiria atualizar todos os pedidos a cada mudança. A junção é feita só quando necessário ($lookup).

Aggregation Pipeline - faturamento por evento

db.pedidos.aggregate([
  { $match:  { status: "pago" } },
  { $unwind: "$itens" },
  { $group:  { _id: "$eventoId",
      ingressosVendidos: { $sum: "$itens.quantidade" },
      faturamento: { $sum: { $multiply:
        ["$itens.quantidade", "$itens.valorUnitario"] } },
      qtdPedidos: { $addToSet: "$_id" } } },
  { $lookup: { from: "eventos", localField: "_id",
               foreignField: "_id", as: "evento" } },
  { $unwind: "$evento" },
  { $project: { titulo: "$evento.titulo", cidade: "$evento.cidade",
      ingressosVendidos: 1, faturamento: 1,
      qtdPedidos: { $size: "$qtdPedidos" } } },
  { $sort: { faturamento: -1 } }
])

RPOP fila:pedidos:pagamento           "pedido:7"

Fluxo 1 - cache da página do evento

1. GET cache:evento:8→ (nil)
cache miss
→
2. MongoDBdb.eventos.findOne({_id:8})
documento permanente
→
3. SETEX cache:evento:8 300 '{...}'resumo guardado por 5 min
→
4. GET cache:evento:8→ JSON
cache hit
→
5. TTL cache:evento:8→ (integer) 300
tempo restante
redis> GET cache:evento:8
(nil)                                              # cache miss
mongosh> db.eventos.findOne({ _id: 8 }, { titulo: 1, cidade: 1, data: 1, "setores.preco": 1 })
{ _id: 8, titulo: 'Rock in Minas 2026', cidade: 'Belo Horizonte', ... }
redis> SETEX cache:evento:8 300 "{\"titulo\":\"Rock in Minas 2026\",\"cidade\":\"Belo Horizonte\",\"precoMinimo\":200}"
OK
redis> GET cache:evento:8
"{\"titulo\":\"Rock in Minas 2026\",\"cidade\":\"Belo Horizonte\",...}"   # cache hit
redis> TTL cache:evento:8
(integer) 300

MongoDB = fonte da verdade · Redis = resumo temporário para leituras repetidas. Quando o TTL chega a zero, o próximo acesso é um novo miss.

Temporário / rápido (Redis)

Conclusão

MongoDB e Redis são complementares: o MongoDB guarda e consulta os dados permanentes com flexibilidade; o Redis entrega expiração automática, rankings sempre ordenados, filas e conjuntos em memória. Juntos, cobrem tanto o histórico quanto a experiência de compra em tempo real.
